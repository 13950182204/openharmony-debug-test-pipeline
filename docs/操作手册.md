# OpenHarmony 调测闭环 —— 插件流程与操作手册

> 适用：`openharmony-debug-test-pipeline` **1.2.1+**（DSH 运行时插件）
> 更新：2026-11-05 ｜ 依据：真实 MR（226 / A333）端到端演练 + 两次真机 OTA 实测 + DH-76AM-HS26A ACTS 豁免实践

本手册覆盖两件事：**流程**（每个阶段到底做什么、证据是什么）与**操作**（怎么跑、怎么看、坏了怎么修）。

## 一、一分钟看懂

```
测试报告/问题 ──> 分诊 ──> 修复 ──> 提 MR ──┐
                                            │（平台自动）
                        GitLab 流水线 openharmony-mr-gate
                                            │
                     Jenkins 门禁 OpenHarmony-V6.1-MR-Gate
                                            │
                     芯片构建 OpenHarmony-V6.1-MR-<chip>  ── 归档固件 + out/ota/*.zip
                                            ▲
                    ┌───────────────────────┴───────────────────────┐
                    │  本插件 ci 阶段：只读观察 + 按 MR 身份认领      │
                    └───────────────────────┬───────────────────────┘
                                            ▼
                        受信任 phase-3 单元：取包 → 预检 → OTA → 回归 → MR 证据评论
```

**核心边界**：插件**不触发任何 Jenkins 构建**。构建由平台（GitLab → Jenkins 门禁）自动完成，
插件只做"观察 + 认领 + 验证"。OTA 与回归是真实设备动作，必须授权。

## 二、流程详解

### 阶段总表

| # | 阶段 | 用什么 skill | 产出（写入流水线状态） | 真实动作 |
|---|---|---|---|---|
| 1 | report | —（编排 skill 内置） | `reportDir` | 无 |
| 2 | triage | `openharmony-test-report-triage` | `triageSummary`（根因/模块/产品侧 or 测试侧） | 无 |
| 3 | fix / 3b waiver | `karpathy-guidelines` / `openharmony-waiver-draft` | `fixSummary` / `waiverRecords` | 改代码（本地）；豁免资料规范见第六节 |
| 4 | mr | `glab-mr-submit` | `mrIid`、`mrUrl`、`sourceBranch` | **创建 MR + 六维审查** |
| 5 | ci | `openharmony-ci-orchestrator` | `pipelineId`、`pipelineStatus`、`gateBuildUrl`、`otaPackage` | **无**（只读） |
| 6 | ota | `openharmony-ota-upgrade`（由 phase-3 单元驱动） | `otaPackage`、`otaSerial`、`otaResult` | **刷机** |
| 7 | regression | phase-3 profile 驱动 | `regressionResult` | 设备回归 |
| 8 | done / 回 fix | — | 汇总 | 回归失败则回到 4 |

### 铁律（优先级高于各阶段默认做法）

1. **测试侧问题不得靠改用例通过**：判定为用例/测试包/环境导致时，走 waiver 路径产出豁免证据，
   禁止改用例源码、放宽断言、跳过用例；豁免资料的目录、三节式与平台字段必须按第六节执行。
2. **只有根因在产品/框架/服务/驱动侧才进 fix**，并继续走 MR → CI → OTA → 回归。
3. **CI 阶段没有"触发"动作**：不能为了"快点跑"去自己 POST Jenkins。
4. 设备操作前必须 `hdc list targets` 确认目标；真实动作等用户授权。

## 四、状态机与字段

### 4.1 run 状态（`~/.local/state/openharmony-ci-orchestrator/runs/<run-id>.json`）

```
gate_pending ──> gate_succeeded ──> build_succeeded ──> (phase3 结果)
   │                    │
   │                    └─> blocked（认领失败：身份不符/设备变体不符/门禁构建被清理/无凭据）
   ├─> gate_failed    （平台流水线失败）
   ├─> gate_aborted   （取消/跳过）
   └─> gate_not_in_scope（目标分支不在门禁白名单：**没有固件验证**）
```

### 4.2 phase3 状态

| 状态 | 含义 |
|---|---|
| `not_requested` | 未登记 phase-3 profile（只观察，不刷机） |
| `not_started` / `running` | 已认领构建，单元运行中 |
| `passed` | OTA 成功 + 回归 PASS |
| `inconclusive` | OTA 成功，但只跑了 smoke（**不谎报功能通过**） |
| `failed` | 预检/传输/刷机/回归失败（带证据） |
| `dry_run` | 包演练（下载校验真包，不碰设备） |
| `waiting_for_device` | 设备池当前无在线设备（**非失败**，冷却后自动重试） |

### 4.3 关键字段

| 字段 | 说明 |
|---|---|
| `trigger.platform.pipeline_id / pipeline_status / pipeline_sha` | 平台流水线事实 |
| `trigger.platform.gate_build_url / gate_build_number` | 汇总门禁构建 |
| `trigger.platform.gate_plan.chips` | 本次门禁实际构建了哪些芯片 |
| `trigger.platform.stale_source` | 门禁构建的提交 ≠ 登记提交（会被阻止，平台重跑后自动解除） |
| `trigger.chip` | 本 run 要验证的芯片（由 `--phase3-profile` 决定） |
| `build.url / number / artifacts` | 认领到的芯片构建与归档清单 |
| `build.device` | 该次门禁构建实际使用的设备变体（`<chip>_<variant>`，已与 profile 白名单、gate plan 交叉核对） |
| `build.adopt_error` | 认领失败原因（含可操作提示） |
| `phase3.artifact_resolved` | 实际选中的包名（有序候选命中结果） |
| `phase3.package.sha256 / target_version / source_versions` | 包事实 |
| `phase3.attempts[].identity_notes` | 设备身份差异（**仅证据**，不阻断） |
| `phase3.attempts[].skipped_write` | 已在本构建固件上，未重复刷机 |
| `phase3.offline_devices` | 本次运行时离线的池内设备 |

### 5.1 日常：一个 MR 从提交到验证

```bash
cd /home/cx/os/openharmony-debug-test-pipeline

MR=<iid>; SHA=<该 MR 当前 head sha>; TARGET=v6.1.0.35_lts

# ① 登记 run（只读观察，不触发构建）
python3 $S/ci_orchestrator.py observe \
  --mr-iid $MR --source-sha $SHA --target-branch $TARGET \
  --repo-dir /home/cx/os/openharmony-debug-test-pipeline \
  --phase3-profile a333-2g-primary-standby --agent-sandbox danger-full-access

# ② 平台跑完后推进（定时器也在每 5 分钟做同一件事）

# ③ 看结果
cat ~/.local/state/openharmony-ci-orchestrator/runs/<run-id>.json
systemctl --user status 'openharmony-ci-phase3@<run-id>.service'
```

不想刷机、只想验证"包能不能拿到、版本对不对"：第 ① 步加 `--dry-run`。

### 5.2 恢复与干预

| 场景 | 命令 / 动作 |
|---|---|
| 认领失败（凭据、门禁构建被清理） | 修好环境后 `ci_orchestrator.py rearm --run-id <id>`，再 `reconcile` |
| MR 更新导致 `stale_source` | 在 GitLab 重跑该 MR 流水线；插件会自动解除（流水线 SHA 回到登记值） |
| 平台流水线失败 | 按评论/链接定位失败作业，修好重提或重跑平台流水线 |
| 设备池全离线 | 不用管：`waiting_for_device`，设备回来（≤5 分钟冷却）自动继续 |
| 单元卡住/异常退出 | `systemctl --user restart 'openharmony-ci-phase3@<run-id>.service'`（runner 会回收 stale claim 并复用已下载的包） |
| 只想清磁盘 | `python3 $S/ci_orchestrator.py reconcile --prune-days 14 --keep-artifacts 3` |
| 查审计事件 | `python3 $S/ci_orchestrator.py note --run-id <id> "<说明>"`；事件在 JSON 的 `events[]` |

### 5.5 回归：OTA 成功后重跑测试用例

**用户口径**：只重跑第一步测试报告里**出错的整个测试项**（模块级），用 `/mnt/d/ohos/XTS6.1/office`
下可用的 LTS 测试包；**全部用例通过才算 PASS**。

```bash
# 1) 分诊阶段把失败测试项登记进流水线状态（**硬约定**，字段名固定）
#    failedModules：xdevice -l 用的**模块名**（= result/<X>.xml 的 <X>，不是测试类名）
#    failedCases  ：["模块名#用例名", ...] 清单（不是数量）
python3 scripts/pipeline_state.py set triage '{
  "failedModules": ["DctsDmsFaTest", "DctsDmsFwkStagePermissionTest"],
  "failedCases": ["DctsDmsFaTest#SUB_DMS_StandardOs_..._0500"],
  "modules": {"DctsDmsFaTest": {"tests": 45, "failed": 1, "cases": ["SUB_DMS_..._0500"]}}
}' --file ~/.dsh/pipeline-state.json
# 形状不合约定会被当场拒绝（例如把数量写成 failedCases）

# 2) 登记 phase-3 时带上回归 profile（携带 xts-rerun 动作）
python3 skills/openharmony-ci-orchestrator/scripts/ci_orchestrator.py observe \
  --mr-iid <iid> --source-sha <sha> --target-branch v6.1.0.35_lts \
  --repo-dir /home/cx/os/openharmony-debug-test-pipeline \
  --phase3-profile a333-2g-primary-standby \
  --regression-profile xts-rerun-lts-f \
  --agent-sandbox danger-full-access
```

OTA 成功后 runner 会：

1. 从流水线状态取模块清单（或 profile 的 `modules`）；
2. 调 xdevice `<action> <task> -c config/user_config.xml -sn <serial> -l <模块...> -rp <报告目录> -tcpath ... -respath ...`；
3. 解析报告目录里的 `summary_report.xml` 与 `result/*.xml`；
4. 判定：**全部通过 → PASS**；任何用例失败 → FAIL；模块没跑起来（`unavailable='1'`）或没有任何用例记录 → `INCONCLUSIVE`；
5. 失败用例写进 MR 评论，交给 `openharmony-test-report-triage` 做根因定位。

> **交接契约**：这份状态文件是「分诊 → 回归」之间**唯一**的交接物。`failedModules` 是
> xdevice `-l` 的**模块名**（HAP 模块名），**不是**报告 `<testsuite name>` 里的测试类名——两者
> 长得像但属于不同命名空间。`pipeline_state.py set triage` 会校验形状与命名提示，写错当场报错。

> ⚠️ **必须记住的一条判据**：xdevice 对"模块根本没跑起来"也会 **exit 0**，报告里只有
> `unavailable='1'` 与 `message=[Environment-...]`。所以**绝不能按退出码判定**，只能解析报告
> （`test_harness.verdict`，已按此实现并有用例覆盖）。

**执行宿主：必须在 Windows 侧跑 xdevice（本机实测结论）**

| 路径 | 结论 |
|---|---|
| WSL 直接跑 xdevice | **不可行**：xdevice 用自带的 Python hdc 客户端连 `127.0.0.1:8710`。Windows 的 hdc 只监听自己的 loopback（WSL 是 NAT，宿主 IP 也不可达），WSL 自带原生 hdc 又看不到设备 → 只会得到 `unavailable: Test source required 1 devices, actually 0 devices were found`。 |
| usbipd 把 USB 交给 WSL | **不可行**：WSL 内核无 `vhci-hcd`。 |
| **Windows 侧执行（已跑通）** | `runner_host: "windows"` + `windows_python` 指向装好 xdevice 的 Windows Python；WSL runner 经 interop 调用，参数自动换算成 Windows 形式，报告写在 D 盘，WSL 侧直接解析。 |

实测证据（MR 226 用的同一台 A333）：`ActsAACommandPrintSyncTest` → `total=16 passed=16 failed=0` → **PASS**。

在 Windows 侧准备一次 xdevice（新机器/重装时）：

```bat
:: 用运行器自带的包安装（依赖很轻：requests）
"C:\Users\<you>\AppData\Local\Programs\Python\Python38\python.exe" -m pip install --user ^
  D:\ohos\XTS6.1\office\acts-LTS-f\tools\xdevice-0.0.0.tar.gz ^
  D:\ohos\XTS6.1\office\acts-LTS-f\tools\xdevice_ohos-0.0.0.tar.gz ^
  D:\ohos\XTS6.1\office\acts-LTS-f\tools\xdevice_devicetest-0.0.0.tar.gz
```

两个由真实故障换来的硬要求（已固化在 runner 里）：

1. **cwd 必须是运行器目录**：xdevice 以 cwd 为基准找 `config/<task>.json`，用 `-c` 指定别的路径
   仍会报 `[Environment-0101015] Task file does not exist, file name: acts.json`。
2. **输出要容错解码**：interop 调用的 cmd.exe 按控制台代码页输出 GBK 字节，严格 utf-8 解码会抛
   `UnicodeDecodeError` 让整步失败（已用 `errors="replace"`）。

## 六、豁免资料规范（waiver）

> 来源：2026-11-05 DH-76AM-HS26A ACTS 豁免实践（14 模块 / 34 套件 / 44 用例）
> 差异说明：原计划 E 组（searchTest_003）只重跑不豁免；后因整模块 `-l` 在 2026-11-05 两轮报告
> 均为 2 failed、单套件 `-s class` 四轮 3/3 通过，仍定性为测试侧（顺序/焦点竞态）并入豁免，
> 故最终为 44 条用例 / 34 套件（不是最初估算的 43 条 / 33 套件）。

> 口径：**一个模块的一个 Testsuite = 一份 txt + 一份 zip + 一条平台申请**。旧做法「一模块一文件、
> 模块级合并一条申请」已废弃，与本节冲突时一律以本节为准。

### 6.1 目录与拆分（R1 / R2 / R8）

目录固定为 `exemption/<测试大项>/<模块>/`，例如：

```
exemption/Acts/ActsAceEtsModuleLayoutFlex03Test/
  flexItemAlignAutoTest.txt
  flexItemAlignAutoTest-豁免材料.zip
  evidence/flexItemAlignAutoTest-report.txt
```

- `<测试大项>` 是平台分类目录（ACTS 豁免放 `exemption/Acts/`），`<模块>` 就是平台「模块名称(Module)」。
- **一个 Testsuite 一套提交物**：`<套件>.txt` + `<套件>-豁免材料.zip` + 一条平台申请。
- 同一模块的多个 Testsuite 必须**分文件、分申请、分单号**；禁止把多个套件合并成模块级的一条申请
  （合并后查重键、用例清单、附件都无法与平台字段对齐）。
- **解析器/校验器强制**：一个 txt 只能含一个模块 + 一个 Testsuite。发现 `模块#套件#用例` 里的模块或套件
  与所在目录/文件名不一致，直接报错并要求拆分，不做"自动兼容"。

### 6.2 txt 三节式（R3）

每个 `<套件>.txt` 固定三节，标题就按下面写（校验器按标题识别）：

1. **1. 失败用例**：设备行（设备型号/串号）、测试报告行（平台 report 路径或 `report-<序号>`）、
   佐证相对路径，然后逐条列失败用例行，格式 `模块#套件#用例`，可带报告耗时：
   `- ActsAceEtsModuleLayoutFlex03Test#flexItemAlignAutoTest#testFlexItemAlignAutoFlexPadOverflow（报告耗时 2.033s）`。
2. **2. 失败原因**：证据链。要能自洽解释"为什么这是测试侧/环境侧问题"，可含源码行号、实测值、
   复跑结果对照；不要只写"已知问题"。
3. **3. 申请豁免理由**：**全文就是平台「豁免原因」字段**（上限 5000 字）。建议 100–400 字，写清"为什么
   本次不修、影响面、后续计划"；低于 80 字视为说明不清，校验器按警告报出。
   **平台提交用的 records 里 `waiverReason` 必须与本节逐字一致**（用解析器导出 records 即满足：解析器取第 3 节全文，缺第 3 节才退回第 2 节），不要另写一版摘要。

三节都必须非空；标题重复或顺序错乱会被校验器报出（顺序问题仅警告）。

### 6.3 佐证文件（R4）

- 佐证统一放**同模块**的 `evidence/` 下，文件名带 `<套件>-` 前缀：
  `<套件>-report.txt`（报告中该套件失败用例原文摘录）、`<套件>-rerun.log`（复跑日志），
  需要时再加 `<套件>-hilog.txt`。
- txt 正文用**相对本文件**的路径引用：`- evidence/<套件>-report.txt：报告中本套件失败用例原文摘录`。
  不允许引用本模块 `evidence/` 之外的文件，也不允许 `..` 越界。
- 佐证只放本套件的文件：别的套件的前缀、无关截图都不要塞进来（zip 里多放会被校验器列为警告）。

### 6.4 zip 与平台字段（R4 / R5）

- `<套件>-豁免材料.zip` 内含：根级 `<套件>.txt` + 本套件用到的 `evidence/<套件>-*` 文件。
- 平台「豁免附件」只能传**单个 zip 文件**；传目录或散文件平台会报错。
- 平台字段填法：

| 平台字段 | 取值 |
|---|---|
| 测试套分类 | `ACTS` |
| 模块名称(Module) | 模块目录名（如 `ActsAceEtsModuleLayoutFlex03Test`） |
| 测试套名称(Testsuite) | **必填，且只能一个套件**（对应 txt 文件名去后缀） |
| 测试用例名称 | 该套件全部失败用例，英文逗号分隔 |
| 豁免原因 | txt 第 3 节全文 |
| 豁免附件 | `<套件>-豁免材料.zip`（单文件） |

### 6.5 查重、保存与 report 口径（R6 / R7）

- **查重键 = 模块 + 套件 + 用例串**：同一模块的不同套件是不同记录，不要因为模块相同就合并或复用单号。
- **只保存草稿，绝不提交**：人工复核后由人决定提交；插件与脚本都不点"提交"。
- report.zip 口径：平台上传的是产品包 `report/` 打包（`ACTS/report-1`、`report-2`…），
  **按日期命名的 run 目录不能原样当序号**用；系统类型/版本号不写死，按测评编号反查。

### 6.6 校验器（只读）

```bash
python3 scripts/verify_waiver_layout.py \
  --exemption-dir '/mnt/d/ohos/XTS6.1/DHong/DH-76AM-HS26A/exemption/Acts' \
  --records '/mnt/d/ohos/XTS6.1/DHong/DH-76AM-HS26A/exemption/Acts/waiver-records-20261105.json'
```

- `--exemption-dir`：必填，接受 `D:\ohos\...`、`/mnt/d/...` 或普通路径（自动互转）。
- `--records`：可选，`waiver-records-*.json`；校验记录与套件一一对应、用例数一致、`attachmentPath` /
  `attachmentTxt` 与目录一致。
- `--allow-legacy`：可选，历史目录的非规范命名（一模块一文件、模块级 zip、佐证未带套件前缀等）
  只警告不判错；结构性问题（三节缺失、模块/套件混用、佐证缺失、records 不一致）仍然报错。

输出固定为 `汇总：X 模块 / Y 套件 / Z 用例 / N 问题`，逐条列出问题；退出码 `0` 无问题、`1` 有问题、
`2` 参数错误（目录不存在、records 不可解析）。

## 七、异常处理速查

| 现象 | 根因 | 处置 |
|---|---|---|
| Jenkins 读 401/403 + 登录页 HTML | 凭据是旧主机/未配/未成对 | 更新 `jenkins.env` 的 `JENKINS_BASE_URL` 与 `JENKINS_USER/JENKINS_API_TOKEN` |
| 无归档包命中 / 命中多个 | 芯片构建同时归档 `update.zip` 与 `updater_full.zip` | 用 profile 的 `artifact.preferred` 有序候选（`update.zip` 优先，`updater_full.zip` 兜底） |
| `No archived OTA package matched` | 门禁产物被保留策略清理 | 让平台重跑流水线（插件不会自触发构建） |
| 门禁构建找不到匹配 | 被后续 MR 的构建挤出查询窗口 | 缩短"观察→认领"间隔；或重新登记 run |
| `Profile does not allow the gate device` / `Profile rejects Jenkins parameter DEVICE` | 门禁按 MR 改动的设备变体选择 `DEVICE`，构建设备不在 profile 的 `jenkins.devices` 白名单（或 gate plan 与构建参数不一致） | **绝不拿别的变体冒充当次包**：核对 MR 实际改动的 `bootloader/a333/configs/<变体>/`，换匹配变体的 DUT/profile，或在 profile 白名单里显式允许该变体后 `rearm` |
| `stale_source` | 门禁构建的提交 ≠ 登记提交 | 平台重跑该提交的流水线 |
| `OTA transfer size mismatch` | 双宿主 hdc 路径/连接问题 | 已内置 `wslpath -w` 转换；确认设备在线后重跑（自动重试） |
| `source version is not allowed by package` | 设备当前版本不在包内白名单 | 换一台可升级 DUT；或确需支持时扩展板级 `VERSION.mbn` 后重新打包 |
| 设备已在本构建上 | 重复执行 | 自动跳过刷机（`already_on_target`），仍走回归与证据 |
| 单元长时间不返回 | Windows `hdc.exe` 经 WSL interop 卡死 | 已用 `timeout -s KILL` 兜底；必要时 restart 单元 |
| `WSL ERROR: UtilAcceptVsock … accept4 failed 110` | interop 瞬时抖动（实测交互 shell 同时刻正常） | 已内置重试（默认 2 次，`CI_INTEROP_RETRIES` 可调）；非抖动错误不重试 |
| 结果 `INCONCLUSIVE` | 只有 smoke，没有功能回归 profile | 用 `--regression-profile xts-rerun-lts-f` 重跑测试项 |
| 重跑报 `unavailable` | 执行宿主没有可达的 hdc 服务（WSL 侧典型） | 用 `runner_host: "windows"`（见 5.5，已实测跑通） |
| 重跑 base 无模块 | 分诊没登记失败项 | 登记 `artifacts.failedModules` 或 profile 里写 `modules` |

## 八、双宿主环境（本机特有，必须知道）

本机 WSL 的 `hdc` 是 **Windows `hdc.exe`** 的包装器（Windows 侧持有 USB）：

- **本地文件路径必须转换**：`hdc file send` 的本地参数要 `wslpath -w`（插件已内置）。
  原样传 Linux 路径会被拼成 `\\wsl.localhost\Ubuntu-22.04\home\cx\/home/cx/...` 而失败。
- **子进程超时不可靠**：WSL interop 进程可能不理会 Python 侧超时（子进程被杀但管道仍被持有，
  调用方无限阻塞，实测卡 13 分钟）。插件对外部命令统一包 `timeout -s KILL N`。

## 九、身份口径与"升级正确"的判据（用户规定）

**identity 不做硬限制：只要能升级、且升级正确即可。**

- 产品名/型号/品牌/厂商 → 只作**证据**（`attempt.identity_notes`），不阻断；
  门禁包内置的是通用身份（`OpenHarmony 3.2` / `ohos` / `default`），与厂商定制身份不同是正常的。
- 硬门禁只剩"**有 `write_updater` + 正常启动完成**"。
- "升级正确"由三条证据共同证明：
  1. `const.product.firmware.commitid` == 本次构建的源 SHA（最硬）
  2. `/data/updater/updater_result` 含 `|pass|`
  3. `bootevent.boot.completed=true`
- 设备已在本构建固件上时 → `already_on_target`，**不重复刷机**。

需要厂商定制身份（DHong/76A/DNAKE）时，得在平台侧给 A333 门禁补 `XTS_PRODUCT_*` 参数并重新构建。
