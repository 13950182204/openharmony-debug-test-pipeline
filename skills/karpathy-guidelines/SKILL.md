# Karpathy 编码准则

减少常见 LLM 编码错误的行为准则，源自 [Andrej Karpathy 关于 LLM 编码陷阱的观察](https://x.com/karpathy/status/2015883857489522876)。

**取舍：** 这些准则偏向「谨慎优先于速度」。对于琐碎任务，自行判断是否适用。

## 1. 先思考再编码

**不要臆测。不要隐藏困惑。把取舍摆在明面。**

动手实现之前：
- 显式说明你的假设。不确定就问。
- 存在多种解释时，全部列出——不要默默挑一个。
- 存在更简单的方案时，直接说出来。必要时据理力争。
- 有任何不清楚的地方，停下。说出困惑点。提问。

## 2. 简单优先

**能解决问题的最小代码。不做任何投机性设计。**

- 不添加超出要求的功能。
- 不为一次性代码做抽象。
- 不要没人要求的「灵活性」或「可配置性」。
- 不为不可能发生的场景写错误处理。
- 如果你写了 200 行而 50 行就能搞定，重写它。

问问自己：「资深工程师会觉得这过度设计了吗？」如果会，简化。

## 3. 外科手术式改动

**只碰必须碰的。只清理自己造成的混乱。**

修改既有代码时：
- 不要「顺手改进」相邻代码、注释或格式。
- 不要重构没坏的东西。
- 匹配既有风格，即使你会写得不一样。
- 发现无关的死代码，提出来——但不要删。

当你的改动产生孤儿代码时：
- 删除**你自己**的改动造成不再使用的 import/变量/函数。
- 除非被要求，不要删除既有死代码。

判据：每一行被改动的代码都应直接溯源到用户的请求。

## 4. 目标驱动执行

**定义成功判据。循环直到验证通过。**

把任务转化为可验证的目标：
- 「加校验」→「先写非法输入的测试，再让它们通过」
- 「修 bug」→「先写能复现它的测试，再让它通过」
- 「重构 X」→「保证前后测试都通过」

多步任务先给出简要计划：
```
1. [步骤] → 验证: [检查点]
2. [步骤] → 验证: [检查点]
3. [步骤] → 验证: [检查点]
```

强的成功判据让你能独立闭环；弱的判据（「把它弄好」）需要不断追问澄清。
